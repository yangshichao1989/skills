# 代码核验式测试流程文档生成（测本）

目标产物：`测试流程-<链路名>.md`，放在项目 openspec 根目录（与需求文档/验收手册同级）。定义：把"某业务链路怎么测"写成**每个节点有代码证据、每个输入有明确来源**的测本，人和自动化脚本都能照着执行。

## 六步流程

### 1. 读文档收口径

- 读 openspec：`config.yaml`（context/rules）、`specs/`、`changes/`（**进行中 + 归档全部**，不得遗漏已实现功能）、tasks 勾选进度仅作参考。
- 若存在《现行需求》《验收手册》等同级文档，一并读取，提取链路的宣称状态机、接口、前置条件、状态码表。
- 输出：链路宣称口径清单（哪一步、什么状态、调什么）。

### 2. 代码核验（文档说什么不重要，代码是什么才重要）

- 对每个宣称点用源码裁决：控制器 `@RequestMapping`/方法路径、service 状态迁移、前置守卫、注释里的变更标记（如 D30/D37 再修订）。
- 记录 file:line 证据；**发现文档与代码不一致 = 文档过期**，写入 §0 警示表，测本按代码写。
- 每个接口标注核验状态：`已核验`（可给落点）或 `未逐字核验·实现前探测一次`。

### 3. 依赖链闭环（自动化的生死线）

每个节点画三栏「**输入 → 来源 → 产出**」，输入必须追溯到明确生产者。按五类查证：

| 输入类型 | 查证问题 |
|----------|---------|
| ID 传递 | 响应体是否返回 id？不返回则用哪个查询接口反查？ |
| 主数据 | 有无创建 API？没有则降级为固定夹具（env），夹具缺失 → 阻塞不造档 |
| 账号/角色 | 每个角色的登录接口、token 字段、账号来源（env/账号表） |
| 文件 | 上传接口是什么？multipart 还是"先传后带 URL"？ |
| 环境开关 | 短信万能码、支付回调可达性等前置配置 |

查不清的标 ⚠️ 并继续查证，**不允许留"来源不明"的输入**。

### 4. 决策拍板

把一次性决策列成表请用户拍板（不要逐个问）：

- 数据来源：固定夹具 SKU vs 每轮现建？
- 资金路径：真实支付退款 vs 0 元单闭环 vs mock 回调？
- 主数据：线路/仓库/券等脚本现建、固定 env、还是主链不需要？

### 5. 落文档（固定 9 章结构）

```
0 文档警示（与过期文档表述对照表 + 修正后的状态机）
1 目标与非目标（覆盖/不覆盖清单）
2 环境/夹具/secrets 表（键、来源、说明）
3 ctx 变量表（键、写入节点、来源字段）
4 节点依赖总图（ASCII，标注焦点与易错点）
5 节点规格（每节点：需要/来源、动作表[方法路径|关键入参|产出→ctx]、断言、守卫、环境阻塞）
6 失败分类（环境阻塞 | 业务失败 | 实现前探测，三分法定处理方式）
7 状态速查（一行一条状态链）
8 附录（非主链支线，标注接口名是否已核验）
9 修订记录
```

### 6. 校验

- 全部相对链接可点且指向存在文件；
- 每个接口有代码落点或"实现前探测"标注；
- 覆盖该链路所有进行中及归档变更点；
- 修订记录补一行。

## 写作铁律

- 不写"应该大概可能"——查不清就标 ⚠️ 继续查，不允许猜。
- 每条流程结论能回答"凭什么"——能给出 file:line 或标注探测。
- 轮询类断言写清轮询对象、终态、超时；异步副作用（消息消费）断言只认最终态。
- 手工口语版（可选）放 `references/`，接口细节以测本为准。
- 修改流程结论时三处同步：测本正文、§0 警示表、§9 修订记录。

## 参考样例（本项目已产出）

- `B2B-openspec/openspec/测试流程-库存到退款闭环.md` — 成品样例：警示表、ctx 表、节点规格的完整示范。
- `references/example-b2b-invariants.md` — "硬性不变量"章节的写作粒度示例。
- `references/example-b2b-manual-walkthrough.md` — 口语版手工流程示例。

## 多项目适配

- openspec 根目录探测：从工作区找含 `config.yaml` 或 `specs/` 的 `openspec/` 目录。
- 语言/框架无关：后端接口证据 = 路由注解 + 控制器方法；状态机 = service 枚举迁移/守卫；前端项目用页面/组件路径作证据。
- 项目记忆里有项目级约束（如链接校验、9 项文档标准）时，按约束优先级叠加执行。
